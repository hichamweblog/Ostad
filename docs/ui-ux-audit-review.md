## 0. بطاقة القرار — الملخص التنفيذي

### 0.1 الحكم العام

التطبيق **ناضج وظيفيًا وأقلّ نضجًا تجريبيًا**. فيه عمق ميداني حقيقي (رزنامة رسمية، توزيع سنوي، مجالس أقسام، تصدير Word بترويسة مؤسسة) وهو ما لا تجده في معظم أدوات الأساتذة. لكن الطبقة التي يلمسها المستخدم يوميًا — التنقّل، الحفظ، والإفادة البصرية (feedback) — تعمل على **أربع فلسفات تصميم متعارضة** في الوقت نفسه، وهذا هو مصدر معظم الاحتكاك لا العمق الوظيفي.

> **الخلاصة في سطر:** المشكلة ليست «ما يستطيع التطبيق فعله»، بل **«كيف يعرف الأستاذ أنه فعله، وأنه حُفظ، وأنه عاد إلى المكان الصحيح»**.

## 2. خريطة المنتج

### 2.1 البنية التقنية للواجهة

القشرة كاملة في ملف واحد: `app/page.tsx`. كل المسارات الـ13 مجرّد **إعادة تصدير بثلاثة أسطر**:

```tsx
// app/settings/page.tsx  و  app/dashboard/page.tsx  و  البقية
import Page from '@/app/page';
export default Page;
```

**النتيجة المباشرة:** كل عنوان URL يعرض نفس المستند ونفس `<title>`. لا يوجد عنوان صفحة في التبويب، ولا وصف في `metadata` لكل مسار، ولا مشاركة رابط تُنتج معاينة صحيحة. التمييز بين «الإعدادات» و«الأقسام» يحدث فقط بعد تنفيذ JavaScript وقراءة `pathname` (`app/page.tsx:160`).

> 🟧 **UX-001** — المشاركة العميقة تعمل، لكن **التمييز البصري في المتصفح معدوم** (كل التبويبات بنفس الاسم). أثر على المستخدم الذي يعمل بتبويبين مفتوحين (الحضور + النقاط): لا يستطيع التمييز.

## 3. رحلة المستخدم (User Journey)

### 3.1 نظرة عامة على الرحلة

```
الزيارة الأولى
   │
   ├─ شاشة إقلاع (splash) تنتظر cloudReady
   │     └─► إن كان هناك مستخدم: انتظار الشبكة قبل عرض أي بيانات محلية
   │
   ├─ بوابة المصادقة (AuthGate)
   │     ├─ Google OAuth
   │     ├─ رابط سحري بالبريد (magic link)
   │     └─ وضع محلي بعد 2 ثانية فشل
   │
   ├─ التهيئة (Onboarding) — 3 خطوات
   │     └─► «إعداد الأقسام الآن»
   │
   ├─ لوحة التحكم (شبه فارغة لعضو جديد)
   │     ├─ طلب إعداد: مادة + قسم + جدول
   │     └─ مهام تجريبية تُزرع تلقائيًا
   │
   ├─ الحلقة اليومية: الترويسة → FAB «ابدأ الحصة» → الحضور → إنهاء
   │
   ├─ الحلقة الأسبوعية: دفتر النصوص → النقاط → المجالس
   │
   └─ الحلقة الفصلية: الوثائق → تصدير → طباعة
```

### 3.2 المرحلة الأولى — شاشة الإقلاع

`app/page.tsx` يحجب المحتوى حتى `cloudReady` (`hooks/useCloudAppState.ts:330`). المشكلة أن الشرط هو `!user || cloudStatus !== 'loading'` — أي أن **أي مستخدم مسجّل مع شبكة بطيئة يرى شاشة إقلاع بدل بياناته المحلية الموجودة أصلًا**، رغم أن الكاش المحلي محفوظ ومتاح.

> 🟥 **UX-004 (حاجب)** — الأستاذ في قسم بلا شبكة جيدة يفتح التطبيق فيرى انتظارًا، مع أن بياناته كلها في الجهاز. المتوقع في تطبيق Offline-first: **اعرض المحلي فورًا، وزامن في الخلفية**. هذا يخالف وعد المنتج الضمني (PWA + مؤشر «غير متصل»).

**التوصية:** اعكس شرط البوابة — اعرض `local-only` فورًا ثم بدّل الحالة عند وصول السحابة. أبقِ شاشة الإقلاع فقط أثناء أول تحميل بلا كاش.

### 3.3 المرحلة الثانية — المصادقة (`AuthGate`)

الخيارات المتاحة: **Google OAuth** + **رابط سحري**. لا كلمة مرور، لا حساب محلي، لا «الدخول كضيف».

**ما يعمل جيدًا:** بديل محلي بعد ثانيتين، ومقبض واضح: البيانات محفوظة في هذا المتصفح.

**الفجوات:**

| المعرّف | الملاحظة | الخطورة |
|---|---|---|
| UX-005 | **لا شروط استخدام ولا سياسة خصوصية** قبل إنشاء حساب — إشكال قانوني/امتثال في منتج تعليمي | 🟧 |
| UX-006 | الأخطاء لا تُشرح. `app/auth/callback/route.ts` يعيد التوجيه إلى `/?auth=error&reason=missing_code`، والواجهة تعرض نصًا عامًا. سبعة أسباب مختلفة (انتهاء الرابط، خادم غير مهيّأ، فشل التبديل) تُترجم إلى رسالة واحدة | 🟧 |
| UX-007 | **لا مؤشر انتظار على مستوى المزوّد**: بعد النقر على Google لا شيء يخبر المستخدم أن التوجيه جارٍ | 🟧 |
| UX-008 | **المصادقة شرط للاستخدام وليست خيارًا**: أستاذ بلا بريد مهني لا يمكنه تجربة التطبيق قبل إنشاء حساب. لا وضع تجربة بلا تسجيل | 🟧 |
| UX-009 | لا إدارة للحساب: تغيير البريد، حذف الحساب، تصدير البيانات (GDPR-مثل) — غائبة تمامًا عن الإعدادات | 🟨 |

> **ملاحظة سياقية مهمة:** لأن التطبيق يخدم أستاذًا واحدًا على جهازه، فإن **الحساب السحابي هو «نسخة احتياطية + تعدد أجهزة»** لا هوية. يجب أن تعكس الواجهة ذلك: «سجّل الدخول لمزامنة بياناتك» لا «سجّل الدخول للبدء».

### 3.4 المرحلة الثالثة — التهيئة (`Onboarding`)

3 خطوات، كلها اختيارية، تنتهي بزر **«إعداد الأقسام الآن»**.

**الفجوات:**

| المعرّف | الملاحظة | الخطورة |
|---|---|---|
| UX-010 | **لا زر «رجوع»** في أي خطوة — خطوة واحدة فقط «التالي» و«تخطّي». من أخطأ في كتابة اسمه لا يستطيع التصحيح إلا بالإنهاء وإعادة الدخول | 🟧 |
| UX-011 | كل الحقول اختيارية، فلا يخرج المستخدم بأي بيان أدنى. النتيجة: يصل إلى لوحة تحكم فارغة ويظنّ التطبيق معطّلًا | 🟧 |
| UX-012 | لا مؤشر تقدّم بصري واضح (1/3، 2/3) | 🟨 |
| UX-013 | **نظامان للتهيئة**: `Onboarding` مكوّن مستقل، ولوحة التحكم فيها بطاقة إعداد مستقلة. لا يكمل أحدهما الآخر، ولا يعرف أيّهما «انتهى» | 🟧 |
| UX-014 | زر الإنهاء «إعداد الأقسام الآن» ينقل إلى شاشة الأقسام، لا يفتح نموذج إضافة قسم مباشرة. خطوة زائدة | 🟨 |

| وقت آخر حفظ | ❌ | ❌ |

> 🟥 **SAVE-003** — **لا توجد لحظة في التطبيق يقول فيها النظام بثقة: «بياناتك محفوظة في الساعة 10:42»**. كل إحساس الأمان مبني على تخمين.

### 6.5 التوصية المعمارية

اعتمد **نموذجًا واحدًا**، وهو الأنسب لهذا المنتج: **حفظ تلقائي + شريط حالة حفظ موحّد**.

```
┌──────────────────────────────────────────────────────┐
│  ● جارٍ الحفظ…   /   ✓ محفوظ 10:42   /   ⚠ غير محفوظ │  ← شريط رقيق في الترويسة
└──────────────────────────────────────────────────────┘
```

**قواعد التنفيذ:**

1. **مصدر حالة واحد** في `useAppState()`: `saveState: 'idle' | 'saving' | 'saved' | 'error' | 'dirty'` + `lastSavedAt`.
2. **مؤشر عالمي** في `TopHeaderSanad` بدل الشارات المتفرقة.
3. **زر حفظ يبقى فقط** في العمليات ذات المخاطرة الحقيقية (استيراد جماعي، رفع ملف).
4. **`beforeunload`** يُفعّل تلقائيًا عندما `saveState === 'dirty'` — في كل التطبيق.
5. **إعادة تسمية** «حفظ جميع الإعدادات» → «حفظ إعدادات الرزنامة» إن بقي، أو توحيده ليحفظ كل شيء فعلًا.
6. **`ConfirmationDialog`** تستقبل `title` و`description` ديناميكيين بدل «تأكيد الحذف» الثابت.

## 14. خاتمة

المنتج يملك **ميزة تنافسية حقيقية**: فهم عميق لعمل أستاذ التعليم الثانوي في الجزائر، ومستوى تفصيل في الرزنامة والتوزيع والوثائق الرسمية لا يوجد في أدوات عامة. هذه الميزة **لا تظهر** للمستخدم في أول عشر دقائق، لأن طبقة الواجهة الحالية تشغله بأسئلة فرعية: *هل حُفظ؟ أي قسم؟ أين كنت؟*

الإصلاحات الحاجبة كلها **صغيرة تقنيًا** — رسالة خطأ، شرط إغلاق، شريط حالة، مبدّل قسم. لا واحدة منها تتطلب إعادة بناء. لذلك التوصية هي تنفيذ الموجة الأولى كاملة (نحو 8 أيام عمل) **قبل** أي إضافة ميزات جديدة؛ لأن كل ميزة جديدة تُضاف فوق نموذج حفظ غير موثوق ستزيد الشعور بأن التطبيق غير متوقَّع.

**ما بعد الموجة الأولى**، يصبح تحسين الرحلة (بطاقة «حصتك القادمة»، مسار الحضور ← الدفتر ← النقاط) ذا أثر مضاعف، لأن المستخدم سيثق بما يراه ويستطيع الاستفادة من الاختصار بدل أن يتحقق يدويًا من كل خطوة.

**ملاحظة على البيانات القديمة:** المكوّنات المحفوظة سابقاً على مقياس 5 تُقصّ
إلى السقف الجديد عند الترقية، ولا تُقرأ قيم `participationScore` القديمة
كتقدير مشاركة إلا إذا طابقت سلّم التقدير. النقاط الكلية القديمة
(`continuousEval`) تبقى كما هي حتى تُعاد المراجعة من شاشة النقاط.
